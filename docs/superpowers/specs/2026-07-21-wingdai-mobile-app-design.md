# Wingdai Mobile App — Design Spec

วันที่: 2026-07-21
สถานะ: รออนุมัติจากผู้ใช้
ขอบเขต: แอป React Native + Expo — UI ครบทั้ง 4 stack เดินได้ด้วย mock data

---

## 1. เป้าหมายของรอบนี้

สร้างแอป Wingdai ที่ **กดผ่านได้จริงทุกหน้าบนเครื่องจริง** โดยยังไม่มี backend

"เดินได้ด้วย mock data" ในที่นี้ไม่ได้แปลว่าหน้าจอตายที่โชว์ข้อมูลปลอม แต่แปลว่า:

- สั่งอาหารแล้วตะกร้าเปลี่ยนจริง ยอดเงินคำนวณจริง
- กดรับออร์เดอร์ฝั่งร้านแล้วสถานะออร์เดอร์ฝั่งลูกค้าขยับตาม
- ตัวนับถอยหลังทำงานจริง หมดเวลาแล้วมีผลจริง
- สลับ role แล้วเห็นคนละ stack จริง

ต่างจากแอปจริงตรงที่ข้อมูลอยู่ในหน่วยความจำเครื่อง ไม่ได้อยู่บนเซิร์ฟเวอร์ — เมื่อ backend พร้อม เปลี่ยนเฉพาะชั้น data layer โดยไม่แตะ UI

### ขนาดงานที่ต้องรู้ก่อน

ทั้ง 4 stack รวมกันประมาณ **40 หน้าจอ** นี่ไม่ใช่งานรอบเดียวจบ §11 แบ่งลำดับไว้ให้ส่งมอบเป็นช่วง ๆ และเห็นของทำงานได้ตั้งแต่ช่วงแรก

---

## 2. Non-goals

- ไม่ทำ backend (Spring Boot / Go / PostGIS / Redis)
- ไม่ต่อ payment gateway จริง — หน้า PromptPay เป็น mock ที่หน้าตาครบ (§11 ข้อ 3 ของ `claude.md` ยังไม่เลือกเจ้า)
- ไม่ทำ Group Order, โปรโมชั่น, คูปอง, บัตรเครดิต, Web PWA (ตาม §2 ของ `claude.md`)
- ไม่ทำ push notification จริง — จำลองด้วย in-app event
- ไม่ทำ WebSocket จริง — จำลองด้วย event bus ในเครื่อง
- ไม่ทำ CI/CD, EAS build pipeline, store submission

## 4. สถาปัตยกรรม Navigation

นี่คือส่วนที่พังง่ายที่สุดและต้องทำให้ถูกตั้งแต่แรก เพราะ `claude.md` §4 ระบุชัดว่า **ห้ามใช้ role enum แบน ๆ**

### 4.1 หลักการ

`account_type` มีสามค่าเท่านั้น: `user` · `rider` · `admin`

**Merchant ไม่ใช่ account type** แต่เป็น capability ที่งอกบนบัญชี `user` เมื่อมีร้านที่อนุมัติแล้ว
**Customer ordering ก็เป็น capability** ที่บัญชี `rider` มีติดตัวด้วย (ตัดสิน 2026-07-21)

```
capabilities(account) = {
  'customer'  ถ้า account_type ∈ {user, rider}
  'merchant'  ถ้า account_type = user และมีร้านที่ approved
  'rider'     ถ้า account_type = rider และเอกสารผ่านการอนุมัติ
  'admin'     ถ้า account_type = admin
}
```

Navigation อ่านจาก capability set ไม่ใช่จาก `account_type` ตรง ๆ — นี่คือจุดที่ทำให้เพิ่ม capability ใหม่ทีหลังไม่ต้องรื้อ

### 4.2 โครง

```
RootNavigator
├── AuthStack                       (ยังไม่ล็อกอิน)
│     Login · Register · OtpVerify · ChooseAccountType · ForgotPassword
│
└── AppNavigator                    (ล็อกอินแล้ว — เลือกจาก capabilities)
      ├── PendingApprovalScreen     ← rider ที่ยังไม่อนุมัติ: เห็นหน้านี้หน้าเดียว
      │                                ห้ามเข้าถึง stack อื่นรวมทั้งการสั่งอาหาร
      ├── CustomerStack             ← มี capability 'customer'
      ├── MerchantStack             ← มี capability 'merchant'
      ├── RiderStack                ← มี capability 'rider'
      └── AdminStack                ← มี capability 'admin'
```

**Role switcher** แสดงเมื่อมีมากกว่า 1 capability เข้าถึงจากหน้าโปรไฟล์และจาก header
- `user` ที่มีร้านอนุมัติแล้ว → สลับ ลูกค้า ⇄ ร้าน
- `rider` ที่อนุมัติแล้ว → สลับ ไรเดอร์ ⇄ ลูกค้า

**stack เริ่มต้น:** `rider` เปิดแอปมาเจอ RiderStack (งานคือสิ่งที่เขามาทำ) `user` เจอ CustomerStack

### 4.3 กฎเรื่องสิทธิ์ที่ต้องบังคับในโค้ด

1. **ขอสิทธิ์ location เบื้องหลังเฉพาะตอนไรเดอร์อยู่ในโหมดทำงาน** — ห้ามขอตอนไรเดอร์กำลังเลื่อนดูอาหารในฐานะลูกค้า และห้ามขอจากบัญชี `user` เด็ดขาด
2. **ห้ามสั่งอาหารจากร้านตัวเอง** — เช็ค `restaurant.owner_user_id` เทียบกับผู้สั่ง
3. **ห้ามไรเดอร์รับงานส่งออร์เดอร์ที่ตัวเองสั่ง** — กฎใหม่ที่มาพร้อมการตัดสิน A3 เช็คตอน dispatch
4. **ไม่มีทางเข้า admin จากการสมัครสาธารณะ** — ไม่มีปุ่ม ไม่มีลิงก์ ไม่มี deep link

ข้อ 1–3 ในรอบนี้บังคับที่ฝั่ง client เพราะยังไม่มีเซิร์ฟเวอร์ **แต่ต้องเขียนไว้เป็นฟังก์ชันแยกที่ย้ายไปฝั่งเซิร์ฟเวอร์ได้ทันที** ไม่ใช่ฝังเป็น `if` กลาง component

## 5. Data layer — จุดที่ตัดสินว่างานนี้จะเสียเปล่าหรือไม่

เป้าหมาย: เปลี่ยนจาก mock เป็น API จริงโดย **ไม่แตะไฟล์ UI สักไฟล์**

### 5.1 โครงสามชั้น

```
UI Components
      ↓ เรียกผ่าน hook เท่านั้น
TanStack Query hooks          useRestaurants() · useOrder(id) · useAcceptOrder()
      ↓ เรียกผ่าน interface
Repository interface          RestaurantRepo · OrderRepo · RiderRepo · AuthRepo
      ↓ มีสอง implementation
MockRepo (รอบนี้)  |  HttpRepo (เมื่อ backend พร้อม)
```

**กฎเหล็ก:** component ห้าม import อะไรจากชั้น mock โดยตรง ห้ามมีคำว่า `mock` ปรากฏในโฟลเดอร์ UI เลย

การสลับทำที่จุดเดียว:
```ts
export const repos = USE_MOCK ? createMockRepos() : createHttpRepos(baseUrl)
```

### 5.2 Mock ต้องมี state จริง

เก็บใน Zustand store ที่ persist ลง AsyncStorage — ปิดแอปเปิดใหม่ข้อมูลยังอยู่

**Order state machine ต้องทำงานจริงตาม §6 ของ `claude.md`:**
```
created → accepted → preparing → picked_up → delivered
                  ↘ cancelled
```
การเปลี่ยนสถานะที่ไม่ถูกต้องต้อง throw ไม่ใช่ปล่อยผ่านเงียบ ๆ

### 5.3 จำลอง realtime

`claude.md` §5 บอกว่าใช้ WebSocket push ห้าม polling — รอบนี้ยังไม่มีเซิร์ฟเวอร์ จึงใช้ **event bus ในเครื่อง** ที่มีหน้าตา API เหมือน WebSocket client

```ts
realtime.subscribe('order:123', handler)   // API เดียวกับตอนต่อ WS จริง
realtime.emit('order:123', payload)        // เฉพาะ mock
```

จำลองสิ่งที่ต้องเห็น:
- ตำแหน่งไรเดอร์ขยับทุก 3–5 วินาที พร้อม **interpolation ระหว่าง ping** (§5 บังคับไว้ — หมุดต้องเลื่อนลื่น ไม่ใช่กระโดด)
- ออร์เดอร์ใหม่เด้งเข้าคิวร้าน
- ข้อเสนองานเด้งใส่ไรเดอร์

### 5.4 Mock dispatch engine

ทำแบบย่อของ §6.3: เมื่อร้านกดรับออร์เดอร์ → เลือกไรเดอร์จากคะแนน → ยิงข้อเสนอ → นับถอยหลัง 15 วิ → ถ้าปฏิเสธหรือหมดเวลา ยิงคนถัดไป

ไม่ต้องทำ batching และไม่ต้องทำ prep-time prediction ในรอบนี้ — **แต่ interface ต้องเผื่อไว้** เพราะของจริงมี

## 6. Design system

### 6.1 โครง token สามชั้น

```
primitive  →  semantic  →  component
brand-500     bg-surface    button-primary-bg
ink-900       text-primary  card-border
```

**component ห้ามอ้าง primitive ตรง ๆ** ต้องผ่าน semantic เท่านั้น เพราะ semantic คือชั้นเดียวที่ dark mode เกิดขึ้นได้

```
/packages/design-tokens
  primitives.ts      ค่าสีดิบ ระยะ ฟอนต์
  semantic.light.ts  map primitive → บทบาท (โหมดสว่าง)
  semantic.dark.ts   map primitive → บทบาท (โหมดมืด)
  index.ts
```

### 6.2 ชุดสี — ดึงจากโลโก้จริงและวัด contrast แล้ว

ค่าทั้งหมดสกัดจาก `Logo/87ed6ad5-…png` ด้วยการอ่านพิกเซลจริง ไม่ใช่กะจากสายตา

**สีจากโลโก้**
```
ส้มแบรนด์    #FE6227    (H 16° · L 57% · S 99%)
teal เข้ม     #023839    ตัวอักษร "Wingdai" ในโลโก้
ครีม         #FEFBF7    พื้นหลังโลโก้
```

**ไล่เฉดส้ม** (คงค่าสีและความอิ่มตัวเดิม เปลี่ยนแค่ความสว่าง)
```
brand-400  #FE7B4A
brand-500  #FE6227   ← สีโลโก้
brand-600  #FB4601
brand-700  #D23A01   ← สีปุ่มและข้อความ
brand-800  #A92F01
brand-900  #802401
```

**ผลวัด contrast จริง**

| คู่สี | อัตรา | ผล |
|---|---|---|
| teal `#023839` บนครีม | 12.51:1 | ✅ ข้อความหลัก |
| ครีมบน teal (โหมดมืด) | 12.51:1 | ✅ ข้อความหลัก |
| **ขาวบนส้ม `#FE6227`** | **3.00:1** | ❌ **ไม่ผ่าน** |
| ส้ม `#FE6227` บนครีม | 2.91:1 | ❌ ไม่ผ่านแม้ตัวใหญ่ |
| ขาวบน `#D23A01` | 4.83:1 | ✅ ผ่าน |
| `#D23A01` บนครีม | 4.68:1 | ✅ ผ่าน |

**ข้อสรุปที่ต้องบังคับในโค้ด:**

1. **ห้ามทำปุ่มพื้นส้ม `#FE6227` ตัวหนังสือขาว** — เป็นสิ่งที่ทุกคนจะทำโดยสัญชาตญาณเพราะเป็นสีโลโก้ แต่ได้แค่ 3.00:1 ปุ่มหลักต้องใช้ `brand-700 #D23A01`
2. **ห้ามใช้ `#FE6227` เป็นสีข้อความบนพื้นสว่าง** ทุกขนาด — ใช้ `brand-700` แทน
3. `#FE6227` ใช้ได้กับ: โลโก้ ไอคอน พื้นที่ตกแต่ง เส้นเน้น จุดแสดงสถานะ — คือทุกอย่างที่ไม่ใช่ข้อความและไม่ต้องอ่าน

**บทบาทของสีในระบบ**
```
โหมดสว่าง   พื้น #FEFBF7   ข้อความ #023839   ปุ่ม #D23A01   เน้น #FE6227
โหมดมืด     พื้น #023839   ข้อความ #FEFBF7   ปุ่ม #D23A01   เน้น #FE6227
```

โหมดมืดใช้ teal ของแบรนด์เป็นพื้นหลัง ไม่ใช่เทาดำกลาง ๆ — ทำให้โหมดมืดยังเป็น Wingdai ไม่ใช่แอปอะไรก็ได้ที่กลับสี

สีที่เพิ่มทีหลัง (เทากลาง สีสถานะ) ต้องวัด contrast ทั้งสองโหมดก่อนใช้ ห้ามกลับสีจากโหมดสว่างแล้วถือว่าใช้ได้

### 6.3 ตัวอักษร

| บทบาท | ฟอนต์ | เหตุผล |
|---|---|---|
| Headline | **Prompt** (Cadson Demak) | โลโก้ Wingdai เป็น geometric sans ปลายมนตระกูล Poppins — Prompt เป็นฟอนต์ไทยที่ออกแบบมาในตระกูลเดียวกัน หัวเรื่องจึงต่อเนื่องกับโลโก้แทนที่จะดูเหมือนคนละแบรนด์ |
| Body | **IBM Plex Sans Thai** | geometric อ่านยาวเมื่อยตา ตัวเนื้อความใช้ humanist ที่อ่านสบายกว่า |

ทั้งสองตัวอยู่บน Google Fonts ใช้ได้ฟรีในเชิงพาณิชย์

กฎบังคับ:
- `lineHeight` ขั้นต่ำ **1.7 เท่าของ fontSize** — สระบนและวรรณยุกต์ไทยชนกันถ้าต่ำกว่านี้
- **ห้าม `letterSpacing` ติดลบ**
- ราคาใช้ตัวเลขความกว้างคงที่
- `allowFontScaling={false}` ตั้งเป็นค่าเริ่มต้นที่ Text component กลาง ไม่ใช่ไล่ใส่ทีละที่

### 6.4 นโยบาย Glass

React Native ไม่มี `backdrop-filter` ต้องใช้ `expo-blur` ซึ่งบน iOS ใช้ระบบของ OS (สวย) แต่บน Android เป็นการจำลอง (กินเฟรม)

| หน้าจอ | Glass |
|---|---|
| Onboarding, โปรไฟล์, ใบเสร็จ, หน้าสรุปยอด | ✅ ใช้ได้ |
| แผนที่ติดตามออร์เดอร์ | ❌ ห้าม |
| **คิวออร์เดอร์ร้าน (นับถอยหลัง 60 วิ)** | ❌ **ห้ามเด็ดขาด** |
| **ข้อเสนองานไรเดอร์ (นับถอยหลัง 15 วิ)** | ❌ **ห้ามเด็ดขาด** |
| ลิสต์ที่เลื่อนได้ทุกชนิด | ❌ ห้าม |

สองหน้าที่ `claude.md` ทำเครื่องหมาย ⭐ ว่าล้มเหลวไม่ได้ ต้องเป็นพื้นทึบล้วน ไม่มีข้อยกเว้น

## 7. i18n

**ตัดสินใจแล้วว่าทำสองภาษาเต็มตั้งแต่ commit แรก** (ย้ายเข้า Phase 1 เมื่อ 2026-07-21)

- ไทยเป็นภาษาต้นทาง อังกฤษเป็น locale ที่สอง
- เลือกอัตโนมัติจาก locale เครื่อง มีตัวสลับด้วยมือในหน้าตั้งค่า
- **ห้ามมี string ภาษาไทยฝังใน component** ทุกข้อความผ่าน key
- key ตั้งตามความหมาย ไม่ใช่ตามข้อความ (`order.queue.accept` ไม่ใช่ `รับออร์เดอร์`)

**ความเสี่ยงที่ต้องทดสอบทุกหน้า:** ภาษาอังกฤษยาวกว่าไทยเกือบทุกครั้ง ปุ่มที่พอดีในภาษาไทยจะล้นในภาษาอังกฤษ ทุกหน้าต้องดูสองภาษาก่อนถือว่าเสร็จ

รูปแบบที่ต้องแยกตาม locale: วันที่ เวลา และสกุลเงิน (`฿150` กับ `THB 150`)

## 8. รายการหน้าจอ

### 8.1 Auth (ใช้ร่วมทุกประเภทบัญชี) — 7 หน้า
Splash + ตรวจ locale · Login · Register · ยืนยัน OTP · เลือกประเภทบัญชี (user/rider) · ลืมรหัสผ่าน · รออนุมัติ (เฉพาะไรเดอร์)

### 8.2 Customer — 11 หน้า
หน้าแรก (ร้านใกล้เคียง หมวดหมู่ แบนเนอร์ประกาศ) · ค้นหา/กรอง · รายละเอียดร้าน (เมนู ตัวเลือกเสริม สถานะเปิด-ปิด) · ตะกร้า · ชำระเงิน + PromptPay QR (mock) · ติดตามออร์เดอร์ (แผนที่สด) · ประวัติออร์เดอร์ · รายละเอียดออร์เดอร์ + สั่งซ้ำ · รีวิว · โปรไฟล์ + ที่อยู่ · ฟอร์มเปิดร้าน

**ตะกร้าต้องแยกบรรทัด** ค่าอาหาร / ค่าส่ง / ค่าบริการ — §3 หลักการ 2 ห้ามรวบเป็นก้อนเดียว

**"แบนเนอร์ประกาศ" ไม่ใช่แบนเนอร์โปรโมชั่น** — `claude.md` §2 ห้ามระบบส่วนลด/คูปองใน Phase 1 แบนเนอร์ในที่นี้คือประกาศข้อมูล เช่น "เปิดให้บริการย่านใหม่แล้ว" หรือ "ร้านใหม่สัปดาห์นี้" ห้ามมีรหัสส่วนลด ห้ามมีราคาตัดทอน ห้ามมีคำว่าลดราคา

### 8.3 Merchant — 7 หน้า
เปิด-ปิดร้าน · **คิวออร์เดอร์ ⭐** · รายละเอียดออร์เดอร์ · จัดการเมนู · แก้ไขเมนู + ปุ่มของหมด · สรุปยอดขาย · ตั้งค่าร้าน

**หน้าคิวออร์เดอร์คือหน้าที่พังไม่ได้ที่สุดในแอป:** เสียงเตือนดัง นับถอยหลัง 60 วินาที ปุ่มรับ/ปฏิเสธใหญ่ชัด พื้นทึบ ไม่มี blur ต้องอ่านออกในครัวที่แสงจ้าและมือเปียก

### 8.4 Rider — 10 หน้า
ออนไลน์/ออฟไลน์ · **ข้อเสนองาน ⭐ (เต็มจอ 15 วิ)** · นำทางไปร้าน · ยืนยันรับของ + ถ่ายรูป · นำทางไปลูกค้า · ยืนยันส่ง + ถ่ายรูป · รายได้ (วันนี้/สัปดาห์ ออร์เดอร์ต่อชั่วโมง) · ประวัติงาน · โปรไฟล์ + เอกสาร · **สลับไปโหมดลูกค้า**

หน้ารายได้ **ห้ามมีอันดับ ห้ามมี KPI ความเร็ว** — §3 หลักการ 4 ห้ามสร้างแรงกดดันให้ขับเร็ว

### 8.5 Admin — 8 หน้า
แดชบอร์ดแบบเน้นรายการที่ต้องแก้ · รายละเอียดออร์เดอร์ที่มีปัญหา · มอนิเตอร์ dispatch + ปุ่มสั่งด้วยมือ · คืนเงิน/ข้อพิพาท (ระบบเสนอ แอดมินกดยืนยัน) · อนุมัติร้าน · อนุมัติไรเดอร์ · รายงานการจ่ายเงิน · รายงานตัวชี้วัด

**ทุกหน้าแอดมินต้องใช้งานบนมือถือได้เต็มที่** — §3 หลักการ 6 ห้ามออกแบบโดยสมมติว่ามีจอกว้าง

**แดชบอร์ดต้องเป็นแบบ exception-based ตั้งแต่แรก** ไม่ใช่ feed ออร์เดอร์ทั้งหมด: ออร์เดอร์เกิน SLA · ข้อพิพาทค้าง · ออร์เดอร์ที่ยังไม่มีไรเดอร์เกิน N นาที

รวม **43 หน้าจอ**

## 10. เกณฑ์ยอมรับ

แต่ละข้อต้องมีหลักฐาน ไม่ใช่คำยืนยัน

1. **แอปเปิดได้บนเครื่องจริง** ทั้ง iOS และ Android — แนบภาพหน้าจอ
2. **วงจรสั่งอาหารครบวง** ลูกค้าสั่ง → ร้านรับ → dispatch หาไรเดอร์ → ไรเดอร์รับ → รับของ → ส่ง → ลูกค้าเห็นสถานะเปลี่ยนทุกขั้น
3. **นับถอยหลังทำงานจริง** ปล่อยให้หมดเวลาที่หน้าคิวร้าน (60 วิ) และหน้าข้อเสนองาน (15 วิ) แล้วผลลัพธ์ถูกต้อง
4. **Role switching** บัญชีไรเดอร์สลับไปสั่งอาหารได้ และบัญชี user ที่มีร้านอนุมัติสลับไปโหมดร้านได้
5. **ไรเดอร์ที่ยังไม่อนุมัติ** เห็นหน้ารออนุมัติหน้าเดียว เข้า stack อื่นไม่ได้แม้แต่การสั่งอาหาร
6. **กฎสิทธิ์** ทดสอบว่าสั่งจากร้านตัวเองไม่ได้ และไรเดอร์รับงานออร์เดอร์ตัวเองไม่ได้
7. **Dark mode** สลับได้ ทุกหน้าอ่านออก ไม่มีข้อความจมพื้น
8. **Contrast** วัดจริงทุกคู่สีที่ใช้ ทั้งโหมดสว่างและมืด แนบตาราง
9. **สองภาษา** สลับ locale แล้วทุกหน้าไม่มีข้อความล้นและไม่มีข้อความไทยตกค้างในโหมดอังกฤษ
10. **ไม่มี glass บนหน้าต้องห้าม** ตรวจว่าไม่มี `BlurView` ใน 4 หน้าตาม §6.4
11. **Permission** บัญชี user ไม่เคยถูกขอ location เบื้องหลังเลย
12. **สลับเป็น API ได้** เปลี่ยนค่า `USE_MOCK` แล้วโค้ดยัง build ผ่าน โดยไม่ต้องแก้ไฟล์ใน `/features`

## 11. ลำดับการทำ

แต่ละช่วงจบแล้วต้องมีของกดดูได้ ไม่ใช่รอจนจบทุกช่วง

| ช่วง | เนื้อหา | เห็นอะไร |
|---|---|---|
| 1 | Expo + tokens + i18n + ui พื้นฐาน + dark mode | หน้าตัวอย่างที่สลับภาษาและโหมดมืดได้ |
| 2 | Auth + navigator ตาม capability + role switcher | ล็อกอินเป็นแต่ละบทบาทแล้วเห็นคนละ stack |
| 3 | Data layer + mock + state machine + realtime จำลอง | ทดสอบวงจรออร์เดอร์ผ่านโค้ดได้ |
| 4 | Customer stack | สั่งอาหารได้ครบจนถึงหน้าจ่ายเงิน |
| 5 | Merchant stack (คิวออร์เดอร์ ⭐ ก่อน) | ร้านรับออร์เดอร์ที่ลูกค้าสั่งได้จริง |
| 6 | Rider stack (ข้อเสนองาน ⭐ ก่อน) + dispatch จำลอง | ครบวงจรตั้งแต่สั่งจนส่งถึง |
| 7 | Admin stack | อนุมัติร้าน/ไรเดอร์ และจัดการข้อพิพาทได้ |
| 8 | ขัดเกลา + ตรวจตามเกณฑ์ §10 | ผลตรวจครบ 12 ข้อ |

**ครบวงจรจริงเกิดที่ช่วง 6** — ก่อนหน้านั้นยังเห็นภาพไม่ครบ

## 13. คำถามที่ยังเปิด
